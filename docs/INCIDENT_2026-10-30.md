# Incident 2026-10-30 — Coupure électrique et mauvaise cible docker compose

## Résumé

Coupure électrique 2026-10-30 17:49 UTC. Au redémarrage, `docker compose up` a été lancé depuis `backend/` au lieu de la racine. Le fichier `backend/docker-compose.yml` déclarait `container_name: egs-postgres` (hardcodé) mais avec un volume différent (`backend_postgres_data`, vide). Résultat : `egs-postgres` a été recréé sur le volume vide, site "neuf", données invisibles. Aucune perte réelle : PostgreSQL avait fait un crash recovery propre, le volume prod (`gnamba-project_postgres_data`, 102 Mo) était intact.

## Récupération

1. Identification du bon volume dans `/mnt/data/docker-volumes/volumes/` (loop sur `PG_VERSION` + `du -sh`)
2. Validation sur copie (conteneur jetable `postgres:16-alpine`)
3. Recréation d'`egs-postgres` via `docker compose -f docker-compose.yml` (racine) → volume correct
4. Vérification counts : `users=5`, `media_files=34`, `finances=121`, `properties=27`

## Pièges rencontrés

- Un export `DATABASE_URL` dans le shell pollue `${DATABASE_URL}` du compose
- Deux data-roots Docker : `/mnt/data/docker-volumes` (actif) et `/var/lib/docker` (ancien, contient un volume de juin à ignorer)
- `alembic current` depuis l'hôte (`host=/var/run/postgresql`) tape un cluster Debian squelette, PAS la prod. Toujours utiliser `docker exec egs-api alembic`
- L'image `egs-api:latest` était en retard sur le code (`expected_revision=035`) alors que la base était déjà migrée → `/ready` renvoyait 503 à tort

## Prévention

- NE JAMAIS lancer `docker compose` depuis `backend/`
- Vérifier `docker inspect <container>` pour le volume monté avant tout `compose up` après un crash
- Monitoring : alerter si `/ready=503` pendant >5 min
